# Архитектура

Документ описывает, как Felagi Flow устроен сейчас — по фактическому коду, а не
по планам. Отдельно отмечены известные пробелы.

## Компоненты

```
┌────────────┐   HTTP/WS    ┌──────────────┐
│  Браузер    │ ───────────► │ Caddy (:80)  │
└────────────┘              └──────┬───────┘
                                   │ /api/*, /hooks/*, /ws/*  → api:8000
                                   │ всё остальное            → статика SPA (/srv)
                                   ▼
                            ┌──────────────┐
                            │ API (FastAPI)│  REST + WebSocket
                            └──────┬───────┘
                                   │ SQLAlchemy async / asyncpg
                                   ▼
                            ┌──────────────────────────────┐
                            │ PostgreSQL 16                 │
                            │  • таблицы домена             │
                            │  • executions — очередь       │
                            │  • LISTEN/NOTIFY (exec_log)   │
                            └──────────────────────────────┘
                               ▲            ▲            ▲
                               │            │            │
                  Worker ×N ───┘            │            └─── Scheduler ×1
                  (claim + run)             │                 (cron, tick 15s)
                        │                   │
                        ▼                   │
              внешние API (Anthropic, HTTP) │
                                            │
                        API держит LISTEN ──┘
                        → fan-out в свои WS-соединения
```

| Компонент | Роль |
|---|---|
| **Caddy** | Единая точка входа: реверс-прокси `/api`, `/hooks`, `/ws`, `/healthz` на API; отдаёт собранный SPA; SPA-fallback через `try_files`. |
| **API** (`app.main:app`) | REST-эндпоинты, WebSocket live-логов, держит `LISTEN exec_log`. |
| **Worker** (`python -m app.worker`) | Claim-цикл: берёт запуски из очереди и выполняет граф. Масштабируется числом контейнеров. |
| **Scheduler** (`python -m app.scheduler`) | Раз в 15 с забирает созревшие cron-расписания и ставит запуски. Один инстанс на кластер. |
| **PostgreSQL** | Данные + очередь + канал уведомлений. Отдельного брокера нет. |

## Поток выполнения workflow

1. **Постановка в очередь.** Запуск создаётся в таблице `executions`
   (`status='queued'`, `available_at=now()`), пинится `workflow_version_id` —
   версия графа фиксируется на момент запуска. Источники: ручной запуск
   (`POST /api/workflows/{id}/run`), cron-тик планировщика, вебхук
   (`POST /hooks/{token}`).
2. **Забор задачи.** Worker берёт одну готовую строку, помечая `running`:

   ```sql
   SELECT id FROM executions
   WHERE status = 'queued' AND available_at <= now()
   ORDER BY available_at LIMIT 1
   FOR UPDATE SKIP LOCKED
   ```

   `FOR UPDATE SKIP LOCKED` — если строку уже держит другая транзакция,
   Postgres пропускает её вместо блокировки: N воркеров берут разные задачи без
   ожидания и без двойного выполнения.
3. **Выполнение.** Воркер грузит граф пиннутой версии, идёт топологически от
   триггерного узла. Для каждого узла: резолвит `{{ nodes.*.output.* }}` и
   `{{ trigger.payload.* }}`, применяет retry-политику узла (in-process,
   backoff), пишет строку `execution_steps` **и коммитит её отдельно**, а перед
   коммитом шлёт `pg_notify('exec_log', <execution_id>)`. Коммит на шаг нужен,
   чтобы live-логи показывали прогресс, а при падении узла уже выполненные шаги
   остались зафиксированы.
4. **Провал.** Узел исчерпал свои retries → execution помечается `failed` (или
   `queued` с `available_at = now() + backoff`, если это инфра-ошибка и
   execution-level попытки ещё есть). После `max_attempts` → `status='dead'`.
5. **Финал.** Воркер ставит терминальный статус (`succeeded`/`dead`/`canceled`)
   и **в той же транзакции** шлёт финальный `NOTIFY`, чтобы подписчики WS сразу
   получили `finished`, а не ждали таймаута heartbeat.

## Очередь на Postgres

Сознательный отказ от брокера (Redis/RabbitMQ): на целевых объёмах Postgres
тянет роль очереди, и вся система остаётся из одной БД.

- **Забор** — `FOR UPDATE SKIP LOCKED` (см. выше).
- **Владение и heartbeat.** Воркер пишет `locked_by`/`locked_at` и продлевает
  `locked_at` (`heartbeat`) перед каждым узлом и между попытками. Индекс
  `ix_executions_running_locked_at` сканирует только `running`.
- **Reclaim** — функция `reclaim_stale(heartbeat_timeout=60)` возвращает в
  очередь задачи, у которых `locked_at` старше таймаута, не «сжигая» попытку
  (`attempts` не меняется: иначе краш-цикл воркера исчерпал бы `max_attempts`,
  ни разу не выполнив задачу). Воркер вызывает её в начале каждой итерации с
  интервалом `RECLAIM_INTERVAL_SECONDS` (по умолчанию 30 с) — сверка интервала
  идёт в памяти, к БД обращаемся только когда срок наступил (`maybe_reclaim`).
  Reclaim стоит **перед** claim: задачи умерших воркеров возвращаются в пул,
  даже когда своей работы у этого воркера нет. Запуск reclaim несколько раз
  идемпотентен и не оставит «зависших» `running` навсегда.
- **Backoff** при retry — `available_at` в будущем; `claim_next` их пропускает.

## Live-логи: NOTIFY → LISTEN → WebSocket

Канал `exec_log` — один на всех; payload — только `execution_id` (лимит NOTIFY
8 КБ). Источник истины всегда БД: клиент, получив уведомление, дочитывает шаги
из БД.

```
worker:  запись шага ─► pg_notify('exec_log', id) ─► COMMIT
                                                      │ (доставка на commit)
Postgres ────────────────────────────────────────────►│
                       ┌──────────────────────────────┘
                       ▼
API (LISTEN exec_log): payload → очередь каждого WS-соединения этого процесса
                       ▼
клиент: WS /ws/executions/{id} → snapshot, steps, finished
```

Тонкости, важные при отладке:

- **NOTIFY доставляется только на COMMIT** и **схлопывает одинаковые payload'ы
  внутри одной транзакции**. Именно поэтому `pg_notify` идёт *до* `commit`, а не
  после: notify после commit попал бы в следующую транзакцию и уведомления по
  шагам слились бы в одно. Так как payload — один и тот же `execution_id`, коммит
  на шаг обязателен, иначе все шаги дают одну доставку.
- **LISTEN требует выделенного соединения** (asyncpg), не SQLAlchemy-пула:
  `app/api/ws_manager.py` держит один коннект на процесс API и раздаёт
  уведомления в `asyncio.Queue` активных WS-соединений.
- **Несколько реплик API** — каждая держит свой LISTEN, получает NOTIFY сама и
  рассылает только в свои соединения. Redis-фанаут не нужен.
- **WS-протокол:** `snapshot` (состояние на момент подключения + все шаги) →
  `steps` (новые, дедуп по id) → `finished` (терминальный статус) → `close(1000)`.
  Периодически `ping` против idle-таймаута прокси. Коды закрытия: `4401`
  (невалидный токен), `4404` (нет доступа/запуска), `4429` (лимит соединений).
- **Гонка подключения:** подписка оформляется *до* отправки snapshot, поэтому шаг,
  добавленный между снапшотом и подпиской, не теряется (лишние уведомления
  отсеиваются по множеству уже отправленных id).
- **Устаревший snapshot.** Снапшот снимается на подключении (обычно
  `status=queued`, `attempts=0`), а `finished` несёт только `status`/`error`.
  Клиент после `finished` дочитывает актуальные метаданные через
  `GET /api/executions/{id}` (см. `useExecutionLogs`).

## Мультитенантность

Изоляция — на уровне workspace.

- Пользователь → членство в workspace с ролью (`owner`/`admin`/`member`) в
  таблице `workspace_members`.
- **Права по ролям** проверяются зависимостями FastAPI
  (`require_role("owner","admin")` и т.п.). Публикация workflow, управление
  участниками и приглашениями — для owner/admin; чтение и запуск — для member.
- **Проверка доступа к объекту:** эндпоинты, работающие с workflow/execution,
  сначала находят объект, затем проверяют членство в workspace его владельца
  (`_execution_for_member`, `_member_of_workspace`). Нет членства → `403`, нет
  объекта → `404`.
- **Публичные вебхуки** (`/hooks/{token}`) — исключение: доступ по секретному
  токену маршрута, без JWT. Токен — `secrets.token_urlsafe(32)`.
- Все запросы к спискам (workflows, executions, members) фильтруются по
  workspace из пути/токена; тесты изоляции — `tests/test_isolation.py`.

## Внешние зависимости

| Зависимость | Обязательна | Зачем |
|---|---|---|
| **PostgreSQL 16** | да | Данные, очередь, LISTEN/NOTIFY. Без неё стек не стартует. |
| **Caddy** | да (в compose) | Единая точка входа, TLS-терминация в проде, статика SPA. |
| **Anthropic API** | нет | Только узел LLM. Без `ANTHROPIC_API_KEY` узел возвращает ошибку шага `ANTHROPIC_API_KEY is not configured`, остальное работает. |
| **Внешние HTTP-эндпоинты** | нет | Только узел HTTP Request; вызываются самим пользователем. |

Никаких других внешних сервисов нет: retry, очередь, уведомления и планировщик
построены на самой БД.
